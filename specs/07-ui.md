# 07 — UI and environment

The `file://` versus `https://` boundary, the render seam, and styling preservation.
Implements `REQ-601`–`REQ-616`, `REQ-701`–`REQ-703`.

---

## 1. The environment seam

One module, `environment.js`, is the **only** code permitted to read `location` (`REQ-601`). It is the
first fragment in the declared order (`02-architecture.md` §3) because everything downstream may need
it, and it is pure data — no DOM, no storage.

```js
// environment.js — the only module that reads location.
TP.environment = (function () {
  var isFile = location.protocol === 'file:';
  return {
    isFile:           isFile,
    aiEnabled:        !isFile,                                          // REQ-602
    canSaveInPlace:   !isFile && typeof window.showSaveFilePicker === 'function',  // REQ-607
    prefersTextExport: isFile,                                          // REQ-510
  };
})();
```

Three platform behaviours, three booleans, one file. This is `PAT-INV-12`'s discipline — "all
persistence goes through one adapter" — applied to the platform: a platform difference confined to
one module is a configuration; the same difference spread across forty call sites is a bug class.

Today there is **no protocol check anywhere** in the codebase. The nearest thing is
`navigator.gpu` detection (`app/ai/webgpu.js:19-21`), which asks a different question and is
unrelated.

## 3. Why each disabled row is disabled

Stated in descending order of what they actually establish. The order matters: the security argument
is decisive, and the platform argument is the one that must be *verified rather than inherited*
(`PATTERN.md` §10, §11).

### 3.1 Security — decisive

Under `file://`, Chrome and Edge treat **all** local files as one origin (`PATTERN.md` §5.1). Two
facts combine badly:

1. `PATTERN.md` §5.9: any local page can read every document in the shared storage origin, so a
   crafted "document" is a plausible exfiltration vector.
2. The app's cloud mode stores an API key in `localStorage` (`app/settings.js:4,38,47`; documented at
   `README.md:121-133`).

Shipping a key field into a `file://` artifact means any other local file the user opens can read it.
That is a self-inflicted exfiltration vector, and it is created by the very feature that is supposed to
be convenient.

### 3.2 CORS — practical

| Mode | From an opaque origin |
|---|---|
| Cloud (`https://ollama.com`) | `Origin: null`; rejected. Ollama Cloud does not send permissive CORS headers for arbitrary origins — the README already documents this (`README.md:67-78`) |
| Local (`http://localhost:11434`) | Works only with `OLLAMA_ORIGINS=*` (`README.md:57-65`). Even then, `Origin: null` is a special case a server is entitled to refuse |
| CORS proxy | The proxy exists precisely because the direct call is refused. A proxy reachable from `file://` is a proxy that will relay for `Origin: null`, i.e. one that has disabled the protection it exists to provide |

### 3.3 Loading — must be verified

`web-llm` is loaded by a runtime `import()` of a CDN URL (`app/ai/webgpu.js:17,78`). Whether an opaque
origin may import a cross-origin ES module is exactly the kind of platform question `PATTERN.md` §11
says must be tested per browser and recorded either way.

**The design must not depend on the answer.** Disabling the AI subsystem under `file://` is correct
under either outcome:

| If the import… | Then |
|---|---|
| is allowed | AI still ships a key into a shared origin (§3.1) and still needs CORS (§3.2). Still disabled |
| is blocked | AI cannot run at all. Disabled for the reason the platform gives |

This is why the open question (`10-open-questions.md` Q-1) is carried without blocking the design, and
why `REQ-606` can be satisfied by *the same bytes* in both environments: the gate is behavioural, and
the behaviour is correct either way.

### 3.4 The cost

Stated plainly: **a user who only ever double-clicks the file never sees the AI planner.** The README
must say so, and Settings must say so in the app (§4.2). This is the accepted cost of a portable
document, recorded in `ADR-0015`.

## 4. How hiding is implemented

The gate introduces **no new mechanism** (`REQ-609`). Both patterns already exist in the codebase for
the Charging tab's EV gating.

### 4.1 The tab — the existing filter

`activeTabs()` (`app/ui/shell.js:77-81`) already filters `STATIC_TABS` on a per-trip condition:

```js
function activeTabs() {
  const trip = getTrip(getState().currentTripId);
  const isEV = !!(trip && trip.vehicle);
  return STATIC_TABS.filter((t) => t !== 'charging' || isEV);
}
```

The AI condition is the same shape, and is **not** per-trip:

```js
return STATIC_TABS.filter((t) =>
  (t !== 'charging' || isEV) &&
  (t !== 'ai'       || env.aiEnabled)
);
```

`refreshTabs()` (`:101-108`) then re-applies visibility, and `switchTab`'s fallback (`:87`) already
redirects to `itinerary` when the active tab becomes hidden. Both behaviours are inherited for free —
which is the argument for reusing the mechanism rather than adding one.

**Initial state.** The Charging tab ships `hidden` in the shell markup (`index.html:39`) because it is
hidden more often than not. The AI tab must do the same (`index.html:41` currently does not), so a
`file://` open never flashes a tab that is about to be hidden.

### 4.2 The settings card — the existing display toggle

`reflectMode()` (`app/ui/settings-view.js:121-128`) already shows and hides the per-mode blocks:

```js
$('set-webgpu-block').style.display = mode === 'webgpu' ? '' : 'none';
```

The Ollama connection card takes the same treatment, and the explanation replaces it:

```js
$('ai-connection').style.display = env.aiEnabled ? '' : 'none';
$('ai-offline-note').style.display = env.aiEnabled ? 'none' : '';
```

The card is wrapped in one container so the toggle is one line, not ten.

### 4.3 The panel — defence in depth

`renderAIPanel` must also guard, mirroring `renderCharging`'s `if (!trip.vehicle)` empty state
(`app/ui/charging.js:19-22`). If the tab is somehow reached — a stale active-tab state in storage, a
future bug in the filter — the panel renders an explanation rather than a composer that cannot work.

### 4.4 The transport — belt and braces

`ai/transport.js` refuses when `!env.aiEnabled`, so no code path reaches `fetch` or the CDN `import()`
from `file://` even if a UI guard is bypassed (`REQ-708`). The UI guards are for the user; this one is
for the invariant.

## 5. The absence must explain itself

`PATTERN.md` §5.8 makes this a general principle for the pattern's most confusing moment: "The last
case earns a specific explanation naming the browser behaviour… Otherwise the user concludes the
application is broken."

The same applies here, and for the same reason. A user who finds no AI tab in a file they double-clicked
will assume the app is a crippled version of the one they read about. So Settings carries a callout
(`REQ-605`), reusing the existing `.info` class (`styles/main.css:140`):

> **AI planning needs a web address.**
> This planner is running from a file on your disk, where the browser gives it no web identity — so
> it cannot reach an AI service, and it will not store a service key somewhere any other local file
> could read it.
> Open the same planner from `http(s)://` instead and the AI tab appears. Everything else — your
> itinerary, budget, bookings, checklists, history, import and export — works exactly as it does
> here, from the file on your disk.

Three things that copy does deliberately: it names the *browser behaviour*, it gives the *security*
reason, and it says what is *not* lost. The third point is the one that prevents the "broken app"
conclusion.

## 6. The render seam

`PATTERN.md` §5.9 requires that "every payload-derived string enters the DOM as text
(`textContent` / `createTextNode`)", that there be "no `innerHTML`, `outerHTML`, `insertAdjacentHTML`,
`document.write` — anywhere, enforced statically over the **built artifact**", and it names the
failure mode: "one missed field".

### 6.1 What this costs

The present app writes HTML strings and escapes interpolations with `escapeHTML`
(`app/utils/format.js:3`). That is a defensible technique and it is **not** what this spec permits,
because it depends on every one of ~40 call sites remembering:

`ai-panel.js` (`:28,:85,:88`), `bookings.js` (`:17,:27,:215`), `budget.js` (`:21,:45,:118,:155`),
`charging.js` (`:16,:20,:28,:156`), `checklists.js` (`:18,:25,:40,:51,:65,:86`),
`itinerary-day.js` (`:19,:37,:57,:143`), `lodging.js` (`:14,:21,:33,:50`), `modal.js` (`:16,:55`),
`places.js` (`:15,:22,:49,:60,:100`), `settings-view.js` (`:14`),
`trip-editor.js` (`:17,:29,:100,:119`), `trip-list.js` (`:20,:25,:29,:212`).

Three of those sites interpolate **unescaped** values today — `<option>` lists built from internal
constant arrays in `bookings.js:215`, `charging.js:156`, `itinerary-day.js:143`. They are safe because
the arrays are internal constants. They are also exactly how this class of bug starts.

`renderMarkdown` (`app/utils/format.js:35-62`) is safe by construction — it escapes first, then
introduces a whitelist of markup — but it *returns an HTML string*, which under this spec must become
a node-building function. Its escaping-first discipline is preserved; its return type is not.

`PATTERN.md` `PAT-DEC-11` warns this is "the largest workstream in the reference implementation by a
wide margin" and says "budget for it explicitly; it is not a footnote". It is phase 0 in
`01-requirements.md` for that reason, and it is a pure refactor: **no behaviour changes.**

### 6.2 The seam

`ui/render.js` is the only path from data to DOM (`REQ-701`):

```js
TP.render = {
  el(tag, props, children),   // element construction; props are attributes/textContent, never markup
  text(string),               // a Text node
  frag(children),             // a DocumentFragment
  clear(node),                // empty a region
};
```

Every view builds with it. The seam exists so that "no markup from data" is a property of one module
rather than a habit across twelve.

### 6.3 The static check

Runs over the **built artifact** (`REQ-703`), not over the sources, because a source grep can be
defeated by a string concatenation that the build joins, and the artifact is what ships. It has a
known allowlist of exactly one call site: `clone.outerHTML` in the export path
(`06-interchange.md` §6), which serializes a document the app itself built from a fixed template.

Any other occurrence fails the build.

## 7. Styling is preserved

`REQ-610`, `REQ-611`, `ADR-0002`.

| Rule | |
|---|---|
| `styles/main.css` stays the authored stylesheet, **unchanged in content** | It is the source; the build inlines it |
| The design tokens at `:root` (`styles/main.css:1-17`) are used as-is | No new tokens unless a genuine need appears, and then appended in the existing block |
| New UI reuses existing class families | `card`, `card__head`, `btn` (`--primary`/`--sm`/`--danger`/`--ghost`), `info` (`--warn`/`--danger`), `badge` (`--high`/`--med`/`--low`), `empty`, `kv`, `data`, `muted`, `subtle`, `mb0`, `mt`, `flex`, `gap`, `wrap` |
| A genuinely new class is appended in the file's existing section-comment style | The file is organised by comment-delimited sections (Sidebar 30, Main+tabs 52, Forms 65, Cards 89, Itinerary 98, Budget 112, AI panel 121, Settings 139, Toasts 147, Modal 154, Checklists 172, Priority badges 179, Bucket chips 188, Location cards 193, Inline editable rows 198, Responsive 206) |

`ADR-0002` records why the stylesheet is inlined rather than pinned to a CDN. `PAT-DEC-02`'s reference
choice accepts degraded offline styling as an explicit deviation from its own requirements; this
instance inlines instead, because for a double-clickable file offline *is* the requirement.

The only new UI surfaces this spec introduces are the gating callout (§5), the history view
(`04-versioning.md` §8), and the reconcile prompt (`04-versioning.md` §7). All three are `card` + `btn` +
`info` + `badge`. No new visual language.

## 8. Shell and views

### 8.1 The sidebar becomes the registry

| Present | Target |
|---|---|
| A list of trips read from IndexedDB (`app/ui/trip-list.js`) | A registry of known **documents** (`05-storage.md` §4) |
| Selecting a trip sets `state.currentTripId` | Selecting a document loads it — from its file, or from local history if it is already known |
| Deleting removes the trip | Deleting removes the *registry entry*, and says so (`REQ-406`) |
| "+ New Trip" | "+ New Trip" — mints a new document with an empty payload and a root commit |
| "⬆ Import" | "⬆ Import" — detects artifact / JSON / iCalendar and creates a document (`REQ-616`) |

The sidebar's empty state changes wording, and that wording is a requirement: it says "no documents
have been opened here", never "no trips" — because the second reads as data loss (`REQ-406`,
`PAT-AP-09`).

### 8.2 New views

| View | Purpose | Reuses |
|---|---|---|
| **History** | The commit list for the current document: message, author, timestamp, ancestry; the "chain intact" label; revert; compaction | `card`, `data`, `badge`, `muted` |
| **Reconcile** | The divergence prompt: "these two copies both changed; choose one side, or compare". Requires a clean working copy | `modal`, `info--warn`, `btn` |
| **Export** | Format choice, the lossiness disclosure (§3.4 of `06-interchange.md`), self-verification result, and the text fallback | `modal`, `info`, `data` |

### 8.3 Listener conventions

Unchanged (`REQ-613`). The codebase uses two, and new views use whichever fits:

| Convention | Where | Use when |
|---|---|---|
| Delegation on a stable container with `closest()` | `app/ui/shell.js:25-29` (`#tabs`), `app/ui/trip-editor.js:106-109` (`#days-host`) | The container persists across renders |
| Query-and-rebind after render, driven by `data-` attributes | `app/ui/bookings.js:122-133` (`wireRowActions`), `app/ui/trip-list.js:40-46` | The container's contents are replaced each render |

### 8.4 The AI panel's clear-chat control

The AI panel's head carries a **Clear chat** button beside "Plan this trip" and "View itinerary"
(`REQ-413`). It reuses the existing `btn`, `btn--sm` and `btn--danger` classes, so there is no new
visual language and no change to `styles/main.css` (`REQ-610`, `REQ-611`). It is disabled while a run
is in progress — clearing a transcript the loop is still writing to would drop the run's own
messages — and it opens the standard confirmation (`modal.confirm`, danger action) before doing
anything, because the deletion is not recoverable from the app.

The action empties the in-memory transcript for the current document and deletes that document's
stored conversations through `TP.ai.agent` (never storage directly, `REQ-401`), then re-renders so the
empty state persists across a reload. Another document's conversations are untouched.

## 9. Boot and interactivity

`REQ-612`, `PAT-INV-14`. The sequence is in `02-architecture.md` §6.

The present boot (`app/main.js:8-38`) clears a watchdog, prints a status line, loads the store,
registers a listener, initialises the shell, and renders — in that order, with storage first and no
integrity or reconcile step. It is a correct boot for a hosted app and the wrong shape for this one.

| Rule | |
|---|---|
| `PRISTINE` is captured before anything else | A single earlier mutation poisons every future export |
| Integrity runs **before** storage | A corrupt history must not be merged into a store |
| Storage is reached **third**, and its absence is not an error | `PAT-INV-02` |
| Reconcile runs **before** the UI is interactive | Running it against a half-initialised store is the failure `PAT-INV-14` names |
| The boot watchdog from `index.html:64-71` is retired | It exists to explain a failure that no longer happens. Its hash would otherwise be a second inline script to pin (`02-architecture.md` §1.2) |

A visible boot status is still wanted — the sidebar's `#storage-status` (`index.html:23`) is the
existing surface (`app/main.js:16,36,42`) and stays, reporting storage mode and the reconcile outcome.
